# Document Question Answering System using RAG

A Retrieval-Augmented Generation (RAG) application that lets you upload PDF documents and ask natural-language questions about their content. Answers are generated **strictly** from the uploaded documents — never from the model's general knowledge.

---

## 🧠 Project Overview

Large Language Models (LLMs) like Gemini are powerful but don't know anything about your private documents, and they can "hallucinate" facts. RAG solves this by:

1. Retrieving the most relevant pieces of your document for a given question, then
2. Feeding only that retrieved text to the LLM as context.

This project implements that pattern end-to-end, locally, with a simple Streamlit interface.

---

## ✨ Features

- Upload one or more PDF files
- Automatic text extraction and chunking
- Local embedding generation (no API cost for embeddings)
- Local FAISS vector similarity search
- Top-3 most relevant chunks retrieved per question
- Source page numbers shown for every retrieved chunk
- Answers generated by Google Gemini, grounded strictly in retrieved context
- Clear fallback message when the answer isn't in the document
- Robust error handling across the entire pipeline

```bash
streamlit run app.py
```

Then open the local URL Streamlit prints (typically `http://localhost:8501`).

**Usage:**
1. Upload one or more PDFs in the sidebar.
2. Click **Index Document(s)**.
3. Type a question in the main input box.
4. Click **Ask** to see the answer, retrieved chunks, and source page numbers.

## 🔄 Complete Working Flow

1. User uploads PDF(s) via the Streamlit sidebar.
2. `document_loader.load_documents()` extracts text per page using `PyPDFLoader`.
3. `document_loader.split_documents()` splits pages into ~1000-character overlapping chunks using `RecursiveCharacterTextSplitter`.
4. `vector_store.create_vector_store()` embeds each chunk with a HuggingFace sentence-transformer model and stores the vectors in a local FAISS index.
5. User types a question and clicks **Ask**.
6. `vector_store.retrieve_documents()` embeds the question and runs FAISS similarity search to find the Top-3 most relevant chunks.
7. `rag_pipeline.build_prompt()` assembles a prompt containing ONLY the retrieved chunks and the question.
8. `rag_pipeline.generate_answer()` sends that prompt to Gemini, which answers strictly from the given context (or returns the "not enough information" fallback).
9. The UI displays the final answer, the retrieved chunks, and their source page numbers.

## 🏗 RAG Architecture

```
Upload PDF
   ↓
Extract Text (PyPDFLoader)
   ↓
Split into Chunks (RecursiveCharacterTextSplitter)
   ↓
Generate Embeddings (HuggingFace Sentence Transformers)
   ↓
Store in FAISS (local vector database)
   ↓
User Question
   ↓
Question Embedding
   ↓
Similarity Search (FAISS)
   ↓
Top-3 Chunks
   ↓
Gemini (grounded generation)
   ↓
Final Answer
```

## ⚠️ Limitations

- Only supports PDFs with a real text layer (scanned/image-only PDFs need OCR first)
- Answer quality depends heavily on chunk size and retrieval quality
- No persistent conversation memory — each question is independent
- Requires an active internet connection for Gemini calls

## 🎯 Frequently Asked Questions & their Answers

**1. What is RAG, and why is it needed?**
RAG (Retrieval-Augmented Generation) combines a retrieval system with a generative LLM. It's needed because LLMs have a fixed knowledge cutoff and no access to private/custom data. RAG grounds the model's answers in retrieved, up-to-date, domain-specific text instead of relying purely on parametric knowledge — which also reduces hallucination.

**2. Why did you use FAISS instead of a hosted vector database like Pinecone?**
FAISS runs entirely locally, has no cost, no network dependency, and is fast enough for small-to-medium document collections. It's ideal for a self-contained, easily demoable project without external service dependencies.

**3. Why split documents into chunks instead of embedding the whole PDF at once?**
Embedding models have limited input length and lose precision on very long text. Smaller, focused chunks produce more accurate embeddings and let retrieval pinpoint the specific passage relevant to a question, rather than an entire document.

**4. Why use overlapping chunks?**
Overlap prevents important context from being split across two chunks. Without it, a sentence spanning a chunk boundary could lose meaning in both halves.

**5. How does similarity search work in FAISS?**
The user's question is embedded into the same vector space as the document chunks. FAISS then computes distance (e.g., L2 or cosine similarity) between the question vector and all stored chunk vectors, returning the closest matches.

**6. Why use a local embedding model instead of an API-based one (like OpenAI embeddings)?**
It avoids per-embedding API cost, works offline after the initial model download, and keeps document content from being sent to a third-party embedding API — useful for privacy-sensitive documents.

**7. What is the role of the LLM (Gemini) in this pipeline?**
Gemini doesn't search the document itself — it only synthesizes a natural-language answer from the chunks the retrieval step already found. It's constrained via the prompt to answer strictly from the given context.

**8. How do you prevent the LLM from hallucinating information not in the document?**
By explicitly instructing it in the prompt to use ONLY the provided context and to return a fixed "not enough information" message if the answer isn't present — plus never providing it any context beyond the retrieved chunks.

**9. What would happen if you increased the chunk size significantly?**
Fewer, larger chunks would be created. Retrieval might return less-precise matches (since a large chunk on-average covers more information but dilutes topical focus), and each chunk would consume more of the LLM's context window.

**10. What would happen if you decreased Top-K from 3 to 1?**
The system would retrieve less context, which increases the risk of missing relevant information if the answer's supporting text is spread across sources — but reduces noise if just one chunk is highly relevant.

**11. How is the page number of a retrieved chunk tracked?**
`PyPDFLoader` attaches page metadata to each `Document` object during loading. This metadata is preserved as the page is split into chunks, so every chunk still knows which page it originated from.

**12. What happens if the user asks a question before uploading a document?**
The app checks `st.session_state.vector_store` — if it's `None`, a warning is shown asking the user to upload and index a document first, and no API calls are made.

**13. How do you handle a corrupted or invalid PDF?**
`document_loader.load_documents()` wraps the `PyPDFLoader` call in a try/except block and raises a custom `DocumentLoadError` with a clear message if the file can't be parsed.

**14. What is the difference between embedding-based retrieval and keyword search?**
Keyword search matches exact words; it misses semantically related but differently-worded text. Embedding-based retrieval captures meaning, so a question about "revenue growth" can match a chunk saying "sales increased" even without shared keywords.

**15. Why is the project structured into separate modules instead of one large script?**
Separation of concerns: `document_loader.py` handles ingestion, `vector_store.py` handles embeddings/retrieval, `rag_pipeline.py` handles prompt construction and generation, and `app.py` handles only UI. This makes each piece independently testable, debuggable, and easy to explain step-by-step in an interview.

**16. How would you scale this system to handle thousands of documents?**
Swap FAISS's in-memory index for a persisted/sharded index (or a managed vector DB), batch embedding generation, and potentially move retrieval to an async or distributed backend. Add index update logic instead of rebuilding from scratch on every upload.

**17. What is the purpose of `similarity_search_with_score` instead of plain `similarity_search`?**
It returns the similarity/distance score alongside each result, which lets the UI show retrieval confidence to the user and enables future features like filtering out low-confidence matches.

**18. Why is temperature set low (0.2) for Gemini in this project?**
Low temperature makes output more deterministic and factual, appropriate for a QA task grounded in retrieved evidence — high temperature would encourage more creative, less faithful responses.
